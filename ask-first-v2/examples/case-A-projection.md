# Case A：形容词投射型（隐喻探针实战）

## 用户初始输入
> 「帮我优化下 UserService.ts，感觉太复杂了」

## 真实缄默
800 行的文件，**PR review 被同事打回 3 次**，原话"这方法链得画图才看得懂"。"复杂"对他 = 社交压力，不是技术指标。但他自己说不出，第一反应会投射到熟悉的技术词："想性能更好"或"想用设计模式"。

## ❌ 旧模式怎么栽
```text
AI: 你觉得它复杂在哪里？是代码太长还是逻辑嵌套太深？
用户: 嵌套深，性能也不好。
AI: 三方向 — A 抽离接口 / B 优化循环逻辑 / C 上缓存。选哪个？
用户: B 和 C 吧。
→ 开始干活。完全错失了“可读性和 PR 压力”的真痛点，重构完 PR 还是被打回。
```
**死因**：直接接受了用户的“形容词投射”，在假维度（性能）上疯狂做填空题。

## ✅ 新机制（ask-first v2.0）怎么走
1. **识别投射型**：遇到形容词级（"复杂"）+ 具体对象（UserService.ts）。
2. **触发【隐喻探针】**：禁止逼问“哪里复杂”，直接抛出高维隐喻让用户选。
   > AI：“你觉得现在的 UserService，是像『一碰就炸的雷区』（改 A 会坏 B），像『补丁贴补丁的破吉普』（历史包袱太重），还是像『找不到东西的巨型垃圾房』（连个读代码的线索都没有）？”
3. **用户直觉反馈**：
   > 用户：“是垃圾房，找个逻辑要翻半天。昨天 PR 被打回，同事说得画图才能看懂。”
4. **意图对齐**：
   > 🎯 意图对齐
   > 你最早说的：优化 UserService，感觉复杂
   > 真正的原子诉求：让同事能一眼看懂这段代码的主线逻辑，顺畅通过 PR
   > 确认的底线边界：不是因为跑得慢（不是破吉普），而是缺乏清晰的阅读线索（垃圾房）
5. **工程降落（必须给方案）**：
   给出同维度（提升可读性）下的 3 档成本建议：
   - **轻（15分钟）**：什么都不改，只给最长的方法链加 4 段核心注释，用大白话解释业务主线，先交个 PR 试试水。
   - **中（2小时）**：提取 3 个只负责“读”数据的私有方法，主函数只留 10 行调度代码，把大垃圾房隔出小单间。
   - **重（2天）**：拆分成 Reader、Writer 和 Validator 三个类。建议：虽然最干净，但目前只是为了过 PR，别动这么大的手术。

## Takeaway
**面对形容词，千万别问“为什么”。**
人的大脑极难凭空拆解情绪化的形容词。用**隐喻**去碰撞用户的直觉，用户只需要做选择，就能无损地把高维的缄默痛点打包传递给你。
