# Case：约束冲突型

## 用户初始输入

> “帮我重构支付模块，最好今天搞完，别影响任何现有逻辑，也别加测试。”

## 真实判断

这不是普通清晰任务，也不是投射型。它的问题是约束互相冲突：

- “重构支付模块”通常有高风险。
- “今天搞完”压缩验证时间。
- “别影响现有逻辑”要求强回归保障。
- “别加测试”又移除了主要保障手段。

这里不要进入正常 ask-first，也不要照单全收。

## 错误走法

```text
AI: 好，我会今天完成支付模块重构，并保证不影响现有逻辑。
```

这是承诺不可验证结果。

另一个错误：

```text
AI: 你没这个重构时最不爽的瞬间是什么？
```

这回避了真正的问题：约束本身不可同时满足。

## 正确走法

```text
AI: 这几个约束互相冲突：支付模块重构要证明“不影响现有逻辑”，但你又禁止加测试。  
我不会承诺整模块重构。可执行的安全切片是：

- 轻：只整理一个无行为变化的小函数或命名，跑现有测试 / 类型检查。
- 中：先补 characterization test，再重构一个边界清楚的分支。
- 重：拆支付模块前先建立回归测试网，再分阶段迁移。

如果今天必须动，我只做“轻”。
```

## Takeaway

约束冲突时，不要用更多追问掩盖问题。先指出不可能三角，再选择最小可逆切片。
