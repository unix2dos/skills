# Case A：形容词投射型

## 用户初始输入
> 「帮我优化下 UserService.ts，感觉太复杂了」

## 真实缄默
800 行的文件，**PR review 被同事打回 3 次**，原话"这方法链得画图才看得懂"。"复杂"对他 = 社交压力，不是技术指标。但他自己说不出，第一反应会投射到熟悉的技术词："想性能更好"。

## ❌ 旧 skill 怎么栽
```
AI: 三方向 — A 拆函数 / B 抽接口 / C 性能优化。选哪个？
用户: C 吧（投射回应）
AI: 缓存用 Redis 还是内存 LRU？
用户: 你看着办
→ 移交 confidence-check，开始做性能优化
→ 完全错失真痛点（可读性），用户的 PR review 仍会被打回
```

三方向**全是技术解**，没问"为什么今天动它"。"你看着办"被当授权默认值。

## ✅ 新 skill 怎么走
1. **识别投射型**：形容词级（"复杂"）+ 具体对象（UserService.ts）→ 触发动机问题
2. **不接性能投射**："我猜一个反例：是不是不是性能，而是最近某次别人读这文件时给了你不舒服的反馈？比如 PR review、新人接手？"
3. **拒收"差不多吧"**：「最近一次 PR 被打回，同事原话是什么？」逼具体场景
4. **World Model 三问** → 痛点=被怀疑能力 / 理想=同事别再说要画图 / 反例=又被说命名怪
5. **拒收"你看着办"**："上次同事说命名怪，就是因为有人替你看着办过一次。"
6. **失败倒推** → "失败 = 下次 PR 仍被同样理由打回"
7. **给方案 3 强度**（同维度 = 降低 review 摩擦）：
   - 轻 1h：拆那个被吐槽的方法链 + 命名让 ChatGPT review 是否"读起来像人话"
   - 中 1d：抽 read/write 分文件 + 4 行类注释
   - 重 3d：拆成 UserReader/UserWriter/UserValidator + README

## Takeaway
**形容词是情绪代偿，背后必有具体场景。**
触发动机问题的提问不能是"你为什么"，要是"什么具体事让你今天想动它"——逼用户回忆**具体事件**而不是抽象描述。
