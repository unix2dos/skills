## 推荐文章

建议写 1 篇：

1. 《把边界放到服务端：内部 CLI 的设计方法》
   主知识簇：内部 CLI 的服务端边界设计
   推荐理由：这份材料的可迁移价值在于抽象出内部 CLI 的边界设计方法，而不是罗列 db tunnel、部署等待、pgweb 和危险操作确认。文章可以围绕“边界在哪里”建立最小模型，再用四个案例说明网络边界、安全边界、成功边界和资源边界都不能交给本地交互层。

   知识簇结构：
   - 必讲机制：CLI 只是入口；网络边界在 VPC 内的 server；安全边界在服务端数据库 `cooldown_until`；成功边界要观察 revision 和 rollback；资源边界要由 manager 登记端口；任意 localhost 反代会产生 SSRF 风险。
   - 可选补充：日志脱敏；部署状态看不清时不报成功；标题应从“踩坑”改成“把边界放到服务端”。
   - 项目案例：Runway CLI 的 db tunnel、危险操作冷静期、ECS 部署等待、pgweb 反代。
   - 删除内容：按聊天顺序复述问答；把每个 CLI 功能拆成独立教程；过度展开 ECS 或 pgweb 的具体使用方式。

   文章骨架：
   1. 开头提出问题：内部 CLI 功能越多，真正难的是边界归属。
   2. 最小模型：把 CLI、server、数据库、云服务、manager 画成职责分层。
   3. 核心机制一：网络边界放到 server，本地 CLI 不直接进入私有网络。
   4. 核心机制二：危险操作的确认边界放到服务端持久状态。
   5. 核心机制三：部署成功边界不能只看第一阶段状态。
   6. 核心机制四：资源边界用登记端口和日志脱敏保护管理面。
   7. 项目案例：四个 Runway CLI 功能如何共用同一个边界模型。
   8. 明确建议：内部 CLI 默认只做交互入口，把网络、权限、状态和资源授权放到服务端。

## 不推荐单独成文的内容

- `db tunnel 的网络边界`：可以作为最小模型和核心机制，但单独写会遗漏安全、成功、资源边界这个更大的主题。
- `危险操作冷静期`：适合作为服务端安全边界案例，不建议写成单独的确认框设计文章。
- `ECS completed 后继续等待`：是成功边界的一个例子，应服务于主线。
- `pgweb 反代和日志脱敏`：材料里的价值是资源边界和 SSRF 风险，不是 pgweb 使用教程。
