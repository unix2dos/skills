## 推荐文章

建议写 1 篇：

1. 《自建短期日志搜索：用延迟换成本边界》
   主知识簇：用批处理链路换可控成本的短期日志搜索
   推荐理由：材料最有价值的不是“EC2 + ripgrep 很土”，而是把日志搜索需求拆成实时性、成本边界、存储职责、解析机制和使用入口。这个模型可以迁移到很多不需要完整日志平台的小团队排障场景。

   知识簇结构：
   - 必讲机制：Logs Insights 扫描量不可控的原因；分钟级延迟换固定底盘；S3 只是中转；EC2 定时拉取并写本地 gzip；Firehose envelope 与 CloudWatch Logs payload 的双层解析；`rg -z` 对 gzip 日志搜索；适用和不适用边界。
   - 可选补充：S3 保留 1 天的重试语义；按 app/hour 组织文件；`runway logs shell` 或 SSM 作为内部入口。
   - 项目案例：用户通过 shell 进入实例后，用 `rg -z` 搜索 EBS 上最近 7 天的日志文件，没有 API，也不接 OpenSearch。
   - 删除内容：把方案评价为“土不土”；把它扩展成日志平台设计；展开复杂权限、多租户、索引服务和实时查询能力。

   文章骨架：
   1. 先讲清楚需求：这不是替代 CloudWatch Logs Insights，而是给短期历史搜索一个可控成本路径。
   2. 最小模型：CloudWatch Logs 经过 Firehose 和 S3，最终落到 EC2 本地 gzip 文件，再由 `rg -z` 搜索。
   3. 核心机制一：为什么反复改 query 会让按扫描量计费的查询成本变得不可预测。
   4. 核心机制二：为什么 S3 只做 transit，真正可搜的数据放在 EBS。
   5. 核心机制三：Firehose 对象为什么要先拆 envelope，再处理 record 内的压缩 payload。
   6. 项目案例：一次内部搜索入口如何从 shell 到目录再到 `rg -z`。
   7. 明确建议：短期、低频、能接受延迟的历史搜索可以这样做；实时 tail、聚合分析和高可用平台不要这样做。
   8. 常见误区和边界：不要直接对 S3 对象运行搜索；不要让中转桶无限保留；不要把这个方案当成权限隔离完善的日志产品。

## 不推荐单独成文的内容

- `Firehose 文件不就是 gzip 吗`：这是重要误区，但应作为主文核心机制，不适合单独拆篇。
- `S3 为啥只留一天`：它解释 transit 语义，适合放在存储职责章节。
- `EC2 + ripgrep 是否太土`：这是表达方式，不是技术主题，应转成“适用边界”讨论。
- `runway logs shell`：属于项目入口示例，正文只需作为落地案例提到。
