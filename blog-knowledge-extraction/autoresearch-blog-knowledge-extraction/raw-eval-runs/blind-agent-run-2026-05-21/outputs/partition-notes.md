## 推荐文章

建议写 1 篇：

1. 《数据表变大怎么拆：分区、分表、分库分表的选择模型》
   主知识簇：数据表变大时的拆分选择模型
   推荐理由：材料不是 GenLab 的部署清单，而是一个可迁移的数据库扩展决策模型。读者最需要的不是知道某张表最后怎么改，而是理解分区、分表、分库分表和换数据库分别解决什么问题、引入什么成本、默认应该先选哪一个。

   知识簇结构：
   - 必讲机制：分区、分表、分库分表的概念差异；PostgreSQL 声明式分区的最小模型；partition pruning 必须依赖查询条件带分区键；主键/唯一约束要包含分区键；插入没有匹配 partition 会失败；分库分表需要 shard key 和路由。
   - 可选补充：MongoDB 不能逃避拆分问题；RDS 不提供应用可控的底层磁盘物理分区；分表适合租户隔离、冷热路径分离或 schema 分叉后再做。
   - 项目案例：`image_generation_tasks` 和 `video_generation_tasks` 这类任务表可按 `created_at` 月度分区，因为写入带时间，归档也按时间。
   - 删除内容：GenLab 的完整业务背景；具体迁移工单；把 MongoDB 当作逃避建模的捷径来展开争论。

   文章骨架：
   1. 先给默认结论：单库未成瓶颈时，优先考虑 PostgreSQL 表分区，不要过早分库分表。
   2. 用一张对比表解释分区、分表、分库分表和换数据库的区别。
   3. 建立 PostgreSQL 分区最小模型：`PARTITION BY RANGE(created_at)` 和月度 partition。
   4. 讲清 partition pruning：查询必须带 `created_at`，否则分区不会自动带来预期收益。
   5. 讲清约束和写入边界：唯一约束包含分区键，未来 partition 要提前建。
   6. 说明什么时候才分表或分库分表：业务边界明确、冷热路径分离、schema 分叉、单库瓶颈已经出现。
   7. 用 MongoDB 和 RDS 物理分区作为反例，说明换技术栈不能绕开 shard key、路由和热点问题。

## 不推荐单独成文的内容

- `PostgreSQL 声明式分区语法`：它是选择模型的最小实现载体，单独写会变成语法笔记，应放进“最小模型”和“核心机制”章节。
- `MongoDB 能不能解决大表问题`：这是反例和边界，不是主线。应放在“常见误区和边界”。
- `GenLab 任务表怎么改`：这是项目案例，不应写成部署清单。正文只保留 `created_at` 月度分区这个可迁移判断。
