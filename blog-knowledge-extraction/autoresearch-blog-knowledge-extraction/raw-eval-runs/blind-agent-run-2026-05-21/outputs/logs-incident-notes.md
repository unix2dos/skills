## 推荐文章

建议写 1 篇：

1. 《自建历史日志搜索：用 Firehose、S3 和 ripgrep》
   主知识簇：有成本边界的历史日志搜索小系统
   推荐理由：材料不是要证明 Logs Insights 不好，而是能抽象出一种可迁移能力：当团队只需要搜索短期历史日志，并且能接受分钟级延迟时，可以把日志先稳定落盘，再用本地全文搜索换取可控成本和简单运维边界。

   知识簇结构：
   - 必讲机制：需求边界不是实时 tail；CloudWatch Logs 到 Firehose 到 S3 的传输链路；S3 只做 transit；EC2 cron 拉取并落到 EBS；`rg -z` 搜索 gzip；Firehose 外层 gzip 与 record 内层 gzip payload 的解析；`flock` 防止 cron 重入。
   - 可选补充：Firehose buffer 选择 64 MiB / 300 秒；S3 保留 1 天用于失败重试；SSM 作为搜索入口；跨天目录搜索的使用提示。
   - 项目案例：`CloudWatch Logs -> subscription filter -> Firehose -> S3 -> EC2 cron -> EBS /logs -> rg -z`，以及线上只保留最近 7 天历史日志的落地方式。
   - 删除内容：单纯吐槽 Logs Insights 价格；把方案包装成完整日志平台；过度展开权限系统、高可用、多租户和复杂聚合。

   文章骨架：
   1. 先定义问题：不是做日志平台，而是给开发者一个成本边界稳定的 7 天历史日志搜索工具。
   2. 最小模型：画出 CloudWatch Logs 到本地 EBS 的数据流，并说明每一段只承担一个职责。
   3. 核心机制一：用 Firehose 和 S3 把日志从在线查询系统转成可批处理对象。
   4. 核心机制二：EC2 cron 如何把中转对象解析成本地可搜索 gzip，并用 `flock` 保证单实例任务不重入。
   5. 核心机制三：为什么 Firehose 文件不是“解一次 gzip 就完事”，以及如何理解 record 内的压缩 payload。
   6. 项目案例：SSM 进入实例后用 `rg -z` 搜索 `/logs/app/date/hour.gz`。
   7. 明确建议：只在短期历史搜索、低频排障、能接受分钟级延迟时采用；实时 tail、复杂聚合、高可用日志平台继续用专门工具。
   8. 常见误区和边界：不要把 S3 当长期日志库；不要忽略重试与清理；不要把权限隔离和高可用能力默认算进去。

## 不推荐单独成文的内容

- `为什么没用 CloudWatch Logs Insights`：容易写成情绪化工具对比，应放在开头的需求边界和成本模型里。
- `Firehose 双层 gzip 解析`：这是主方案能落地的关键机制，但单独成文会过窄，适合作为核心机制章节。
- `cron 使用 flock`：属于批处理可靠性的细节，放进 EC2 拉取与解析章节即可。
- `SSM + cdlogs + rg -z 搜索入口`：是项目落地案例，不是独立知识簇。
