## 推荐文章

建议写 1 篇：

1. 《大表扩展怎么选：分区、分表到分库分表》
   主知识簇：大表扩展方案的分层选择
   推荐理由：原材料的核心不是某个 PostgreSQL 配置，而是一个可迁移的扩展决策模型：先判断瓶颈来自单表管理、业务边界，还是单库实例容量，再选择分区、分表或分库分表。这个模型能帮助读者避免一上来就分库分表，也能解释为什么换 MongoDB 不能逃避 shard key 设计。

   知识簇结构：
   - 必讲机制：分区、分表、分库分表的区别；分区键和 partition pruning；分库分表带来的事务、唯一约束、跨 shard 查询代价；文档数据库也需要 shard key。
   - 可选补充：提前创建未来 partition；查询尽量携带时间条件；冷热路径不同和 schema 分叉时再考虑分表。
   - 项目案例：GenLab 当前按 `created_at` 做 PostgreSQL 月度分区，保留查询父表的普通表体验。
   - 删除内容：把“终极方案”包装成经验故事；把 MongoDB 当成替代关系型分区设计的完整方案。

   文章骨架：
   1. 先定义问题：大表变大时，先判断是单表维护问题、业务边界问题，还是单库容量问题。
   2. 最小模型：用一张对比表区分分区、分表、分库分表。
   3. 核心机制一：PostgreSQL 分区为什么对应用相对透明，以及为什么查询要带分区键。
   4. 核心机制二：分表什么时候比分区更合适。
   5. 核心机制三：分库分表解决什么，又引入哪些不可忽略的代价。
   6. 反例边界：换 MongoDB 不能绕开数据分布和 shard key。
   7. 项目案例：按 `created_at` 月度分区如何落地。
   8. 明确建议：默认先用分区承接时间型大表，不要把分库分表当第一步。

## 不推荐单独成文的内容

- `PostgreSQL partition pruning`：它是分区方案里的核心机制，但不能独立回答“大表扩展怎么选”，应放在分区章节。
- `业务分表`：它依赖与分区、分库分表的对比才容易讲清楚，应作为决策模型中的一层。
- `MongoDB sharding`：在材料里主要承担反例作用，说明换数据库不能逃避 shard key 设计，不建议单独展开成 MongoDB 文章。
